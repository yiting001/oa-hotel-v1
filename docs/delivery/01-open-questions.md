## 2. 已识别的原文矛盾

1. “4.3 接口申请单”下的截图标题为“借款申请单”，4.6 又出现借款申请单。
2. “4.5”同时用于微信支付宝退款和信用卡退款，编号重复。
3. 合同审批步骤编号在文字中有缺失或重复。
4. 印章流程中出现“⑧⑦印章管理员”的编号错误。
5. 部分流程先写“业主负责人”，后写“业主代表”，是否同角色不明确。
6. 物资申购与领用在源文档中使用几乎相同的财务流程，但业务执行职责不同。
7. 党委发文、党群收文复用了其他截图和审批链，可能只是示意。
8. 收文表单使用“拟稿部门、拟稿人、拟稿时间”，与收文业务语义不一致。

这些内容不能通过代码猜测。开发时应将确认结果写入本文件或 ADR。

## 3. 初步产品决策

| 决策 | 状态 | 理由 |
| --- | --- | --- |
| 首期采用模块化单体 | 建议 | 200 用户规模下简化一致性和部署 |
| 工作流与业务模块分离 | 确定原则 | 避免每个表单复制审批代码 |
| 流程和表单版本不可变 | 确定原则 | 保证历史可重现 |
| 原截图字段全部保留 | 用户要求 | 响应式改版不删除字段 |
| SQLite 只做首期单实例 | 建议 | 满足当前栈，同时保留迁移边界 |
| 先做合同/支出纵向切片 | 建议 | 覆盖最复杂链路，能验证平台设计 |

## 4. 风险登记

| 风险 | 等级 | 缓解 |
| --- | --- | --- |
| 业务流程未确认就同时开发全部模块 | 高 | 按纵向切片交付，流程签字确认后开发 |
| 把流程写死在业务代码 | 高 | 配置化流程版本和办理人策略 |
| SQLite 多写并发和单机故障 | 中 | WAL、短事务、备份恢复、迁移预案 |
| 表单全部存 JSON 导致无法统计和校验 | 高 | 核心字段结构化，JSON 只保存动态快照 |
| 过度抽象拖慢首期 | 中 | 仅对明确变化点使用模式 |
| 响应式页面遗漏旧表单字段 | 高 | 字段字典 + 截图逐项验收 |
| 敏感财务与身份数据泄露 | 高 | 加密、脱敏、最小权限、审计 |
| 组织人员变化导致流程卡死 | 中 | 候选组、兜底人、异常队列 |

## 5. 需求确认方式

建议按模块召开 60–90 分钟确认会，使用以下材料：

1. 表单字段字典。
2. Mermaid 流程图。
3. 角色/节点/动作矩阵。
4. 条件分支和金额阈值表。
5. 打印样张。
6. 待确认问题。

确认结果按版本记录，避免在聊天中零散变更后失去追踪。
